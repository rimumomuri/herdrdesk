# Public release and dashboard replacement

## 1. Portable Core connection

Discover Core from user-configured or standard executable locations. Put terminals into the structure panel using Core identity, Herdr placement, and optional team labels. Validate every user-initiated operation against the selected address and session. In test sessions, use a dedicated Core socket and local data directory.

## 2. Localized dashboard

Use the approved graphite dashboard with operational gauges, team and terminal structure, handoff activity, and a shared chat/terminal detail panel. Resolve interface strings in English, Korean, or Japanese. Use the system's preferred supported language on first launch and persist the user's choice. User-generated content and terminal output are displayed verbatim.

## 3. Keep operational features comparable

Carry the existing explicit question and approval links, role-based history, work journals, attachment drafts, read marks, and duplicate-send recovery forward. A message sent by Core, a receipt acknowledged by an agent, and a product verification result are distinct. Preserve existing personal profile data only in the installed personal app or a local migration. The public preview must start with a clean profile.

## 4. Verify before replacing the installed view

Run Swift and JavaScript tests and exercise the signed candidate with sample local and remote terminals. Compare retained drafts, histories, question state and read-only terminal behavior. Compare idle work and confirm that handoff animations are finite. Preserve an installed-app backup and an immediate way to return to the existing view.

## 5. Publish

Prepare a clean source history with synthetic examples, a project license, third-party notices and English release notes. Run the [release checklist](releasing.md) before making a repository public. Ship a signed and notarized desktop binary only after distribution verification.
